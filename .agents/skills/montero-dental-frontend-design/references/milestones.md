# Frontend milestone execution

Use with [SKILL.md](../SKILL.md) and [verification](verification.md). The [implementation plan](../../../../docs/work-items/frontend-modernization/FRONTEND-ONLY-IMPLEMENTATION-PLAN.md) sets the increment order; it does not authorize BUILD.

1. **PLAN:** Read instructions, design system, specification and previous handoff. Inspect branch, HEAD, status, current accepted functional baseline and affected source read-only. Verify remote baseline when the task requires it; report drift and obey any stop gate before editing. Preserve unrelated work. Do not treat stale local tracking refs as live `main` evidence. Use a clean topic branch only when branch creation/switching is authorized; no reset, blind stash or overwrite.
2. **SPEC:** Record the approved presentation goal, acceptance criteria, explicit file allowlist and protected functional regions inside each view. Separate documentation setup from application BUILD. Identify contrast/reflow/keyboard requirements and the exact baseline for requests, permissions, navigation, modal behavior, financial/print output and persistence. Record unknown policy questions; never invent a rule to clear a gate.
3. **BUILD:** Start only after explicit frontend BUILD authorization. Make small scoped CSS/static-view presentation changes within the allowlist and existing stack. Work autonomously through approved styling subtasks and in-scope regressions. Preserve executable PHP/JavaScript even inside allowlisted views. A necessary functional, security, backend, route, API, database or workflow amendment needs separate authorization; document it and continue independent work. Never copy application changes from Draft PR #8 or add a dependency/build system.
4. **VERIFY:** Follow verification.md. Compare the actual diff with the allowlist and functional baseline, run available relevant checks, repair only in-scope regressions and retest affected cases. Mark unavailable evidence honestly; historical results and intercepted responses are not fresh runtime/persistence passes. Do not start services or mutate demo data merely to verify documentation.
5. **REVIEW:** Inspect every modified and new file, links, tokens, whitespace and preservation evidence. Update one task-specific handoff with baseline, branch, scope, commands/results, blockers, owner-review findings and the first concrete next action. Use `READY_FOR_REVIEW` only after that stage's required documentation/preservation checks pass; state any remaining runtime or acceptance gates explicitly. Stop at review unless the user separately authorized a subsequent action.

Human authorization is required for commits, pushes, pull requests, merges and deployment. No automatic publication, local checkpoint commits, PR creation or deployment is implied by this workflow. Staging/branch writes also follow repository authorization. Sanitized handoffs remain local until a separately authorized commit/push; Git cannot carry uncommitted work to another device.

Rollback planning must describe only the increment's scoped diff, account for later overlapping accepted changes and require separate execution authority. Do not restore whole historical view/CSS files over newer security/correctness work; no database reset or financial recovery belongs to a presentation rollback.
